## 🗄️ Завдання 1: SQLite-база та шар доступу до даних

В рамках цього завдання було спроєктовано та реалізовано реляційну базу даних SQLite, розроблено механізм початкового заповнення (seed) та створено шар доступу до даних (Repository Pattern) без використання ORM.

### 🛠 Основні реалізовані компоненти:

1. **Схема бази даних (`schema.sql`):**
   * Створено таблицю `categories` (`id`, `name`) з унікальністю назв (`UNIQUE`).
   * Створено таблицю `records` (`id`, `code`, `title`, `category_id`, `value`, `status`).
   * Реалізовано зовнішній ключ `FOREIGN KEY (category_id) REFERENCES categories(id)` для забезпечення цілісності зв'язків.
   * Додано обмеження `CHECK` на рівні БД:
     * `value` (навчальна оцінка ризику) має тип `REAL` і обмежується діапазоном від `0.0` до `10.0` inclusive.
     * `status` приймає лише значення з множини `('new', 'in_progress', 'done')`.
   * Додано індекси для прискорення пошуку за полями `category_id` та `status`.

2. **Модуль управління БД (`database.py`):**
   * Налаштовано підключення до файлу бази `data/lab3.sqlite3` через стандартний модуль `sqlite3`.
   * Реалізовано обов'язкове виконання `PRAGMA foreign_keys = ON;` при кожному з'єднанні для примусової перевірки цілісності зовнішніх ключів.
   * Створено функцію `initialize_database()`, яка зчитує `schema.sql` та безпечно створює таблиці без видалення наявних даних (`CREATE TABLE IF NOT EXISTS`).

Відкрийте термінал у кореневій папці проєкту та виконайте команду:

```bash
python -m labs.lab02.main demo 
```


3. **Атомарний сідінг даних (`seed.json` та `seed.py`):**
   * Створено JSON-файл із початковими даними для варіанта №13 (3 категорії: `iam`, `storage`, `network` та 8 тестових записів).
   * Реалізовано модуль `seed.py`, який виконує первинне заповнення бази **в межах єдиної атомарної транзакції** (`BEGIN...COMMIT`).
   * Додано перевірку: якщо дані вже присутні у базі, процедура повторного додавання пропускається.

Відкрийте термінал у кореневій папці проєкту та виконайте команду:

```bash
python -m labs.lab03.seed
```

4. **Шар доступу до даних / Репозиторій (`repository.py`):**
   * **Безпека:** усі SQL-запити використовують виключно параметризований синтаксис (знаки `?`), що унеможливлює SQL-ін'єкції.
   * **CRUD для категорій:** створення `create_category()`, отримання `get_all_categories()`, `get_category_by_id()`, видалення `delete_category()`.
   * **CRUD для записів:** 
     * `get_records()` — гнучка вибірка записів із підтримкою фільтрації (`category_id`, `status`, `min_value`), пошуку по назві/коду (`q`), пагінації (`limit`, `offset`) та агрегації назви категорії через `LEFT JOIN`.
     * `create_record()`, `update_record()`, `delete_record()`, `get_record_by_id()`.
   * **Атомарні пакетні операції:** метод `create_records_bulk()` виконує додавання списку записів (1–100 елементів) в одній транзакції. У разі виникнення `sqlite3.IntegrityError` спрацьовує автоматичний `rollback()`, що гарантує відкат усіх змін.


## Завдання 2: Web API за допомогою FastAPI

В рамках цього завдання було розроблено REST API на фреймворці FastAPI з підключенням до БД SQLite без використання ORM (із застосуванням стандартного модуля `sqlite3`).

### Основні реалізовані компоненти:

1. **Валідація та схеми даних (`schemas.py`):**
   * Використано **Pydantic 2** для створення REST-моделей.
   * Налаштовано `extra="forbid"` для заборони передачі незадекларованих полів.
   * Додано сувору валідацію: `value` перевіряється на тип `float` у межах від `0.0` до `10.0` inclusive, а строки очищаються від зайвих пробілів (`str_strip_whitespace=True`).

2. **Шар роботи з базою даних (`repository.py`):**
   * Реалізовано повний набор CRUD-операцій за допомогою безпечних параметризованих SQL-запитів (із символом `?` для запобігання SQL-ін'єкціям).
   * Отримання записів виконується через `LEFT JOIN` з таблицею `categories` для підтягування назви категорії (`category_name`).

3. **Маршрутизація та обробка HTTP-статусів (`routers/`):**
   * **`routers/categories.py`**:
     * `GET /categories` — отримання списку категорій.
     * `POST /categories` — створення нової категорії (повертає `201 Created` або `409 Conflict` при дублюванні).
     * `DELETE /categories/{id}` — видалення порожньої категорії (повертає `204 No Content`, `404 Not Found` або `409 Conflict`, якщо категорія містить записи).
   * **`routers/records.py`**:
     * `GET /records` — фільтрація записів за `category_id`, `status`, `min_value`, текстовий пошук `q`, а також пагінація (`limit`, `offset`).
     * `GET /records/{id}` — отримання запису за ID (`404` при відсутності).
     * `POST /records` — створення одного запису.
     * `PUT /records/{id}` — повне оновлення запису.
     * `DELETE /records/{id}` — видалення запису.
     * `POST /records/bulk` — пакетне створення записів (1–100 елементів) в межах **однієї атомарної транзакції**. У разі помилки або дубліката виконується повний `rollback`.

4. **Головний модуль застосунку (`main.py`):**
   * Використано `lifespan` для автоматичної перевірки та ініціалізації схеми БД під час запуску веб-сервера.
   * Додано обов'язкові сервісні ендпоінти: `GET /ping` (перевірка доступності) та `GET /student` (інформація про студента, групу та варіант №13).
   * Підключено інтерактивну документацію **Swagger UI** (`/docs`).

Відкрийте термінал у кореневій папці проєкту та виконайте команду для запуску:

```bash
uvicorn labs.lab03.main:app --reload --host 127.0.0.1 --port 8000
```


## Перевірка API, збереження даних і транзакцій

У межах цього етапу було проведено комплексне тестування розробленого REST API на відповідність бізнес-логіці варіанта №13, перевірено коректність збереження даних у SQLite та відтестовано атомарність пакетних транзакцій.

### 🛠 Основні реалізовані перевірки:

1. **Сервісні маршрути та перевірка доступності:**
   * **`GET /ping`**: перевірено працездатність сервера (повертає статус `200 OK` та тіло `{"status": "ok"}`).
   * **`GET /student`**: перевірено повернення персональних даних студента (ПІБ, група, варіант №13) з модуля `shared/student.py`.

2. **Отримання та фільтрація даних (JOIN та Query-параметри):**
   * **`GET /categories`**: успішно повертає список усіх 3 категорій (`iam`, `storage`, `network`).
   * **`GET /records`**: перевірено роботу параметрів фільтрації (`category_id`, `status`, `min_value`), пошуку по строках (`q`) та пагінації (`limit`, `offset`). Отримані об'єкти містять поле `category_name`, обчислене через SQL-операцію `LEFT JOIN`.

3. **Валідація даних та обробка помилок (Pydantic 2 & HTTP Status Codes):**
   * **Перевірка межа значення (`value`):** при спробі передати `value` поза межами `[0.0, 10.0]` (наприклад, `15.0` або `-1.0`) FastAPI автоматично повертає статус `422 Unprocessable Entity`.
   * **Заборона незадекларованих полів:** завдяки `extra="forbid"` передача зайвих полів у JSON викликає помилку валідації `422`.
   * **Обробка конфліктів унікальності:** при спробі створити запис із вже існуючим `code` або категорію з наявною назвою API повертає статус `409 Conflict`.
   * **Захист цілісності зовнішніх ключів (FK):** спроба видалення категорії, яка містить пов'язані записи у таблиці `records`, блокується базою SQLite (`PRAGMA foreign_keys = ON;`) та повертає статус `409 Conflict`.

4. **Тестування атомарності пакетних транзакцій (`POST /records/bulk`):**
   * Проведено тест на транзакційну цілісність: надіслано масив із 2 записів, де перший запис є коректним (`V13-ROLLBACK`), а другий містить дублікат існуючого коду (`V13-01`).
   * **Результат:** API перехоплює `sqlite3.IntegrityError`, робить повний відкат (`rollback()`) і повертає `409 Conflict`.
   * **Підтвердження:** наступний запит `GET /records` довів, що перший запис (`V13-ROLLBACK`) **не потрапив до бази даних**, що повністю підтверджує виконанність вимоги атомарності («все або нічого»).

5. **Статичний аналіз та кодувальний стиль (Ruff):**
   * Код проєкту успішно пройшов лінтинг `ruff check labs/lab03` та перевірку форматування `ruff format --check labs/lab03` без жодних зауважень.
